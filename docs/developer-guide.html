Developer Guide

Noorifa Core architecture & extension guide

How the plugin is put together, how a WooCommerce product page actually gets rendered, and how to extend it safely — including exactly how the Pro companion plugin unlocks things.

Overview

Noorifa Core builds WooCommerce single-product pages out of Gutenberg blocks. A "Layout" is just a normal WordPress post (custom post type noorifa_core_layout) whose block content wraps WooCommerce's own rendering — title, price, gallery, add-to-cart, reviews — each as its own block. Nothing is hand-coded per theme; a Layout is resolved fresh on every request and swapped in for the product template.

Three architectural decisions shape almost everything else in the codebase:

  • A Layout is content, not a template file. Store owners build it in the ordinary block editor, the same surface they already know. Layouts\Resolver decides which Layout post applies to which product at request time (see The Layout system) — there's no per-product PHP template to hand-edit.
  • Free/Pro is one codebase plus one filter, not two builds. Licensing\Gate is a plain static class whose is_pro()/has_feature() methods are pure filter lookups, defaulting to false. Nothing Pro-only is physically stripped from the free plugin — a separate companion plugin, Noorifa Core Pro, hooks those filters once a real license is active. See Licensing & the Pro gate.
  • Overriding the product template never breaks WooCommerce's own hooks. The override happens at the whole-template level (template_include), and the fallback template still fires every one of WooCommerce's structural actions (woocommerce_before_single_product, etc.) in their normal positions — so themes and other plugins hooked to those actions keep working around a Layout exactly as they would around WooCommerce's own template.

Everything under includes/ is PSR-4 autoloaded under the Noorifa\Core\ namespace by includes/Autoloader.php, which maps Noorifa\Core\Sub\ClassName to includes/Sub/ClassName.php and guards each require with is_readable() — safe to call class_exists() against a class whose file doesn't exist, with no fatal error.

Boot sequence

  1. plugins_loaded — noorifa-core() resolves Plugin::instance(), which constructs the singleton (protected constructor, only reachable through the Singleton trait).
  2. WooCommerce presence is checked first. If class_exists( 'WooCommerce' ) is false, an admin notice is hooked and the constructor returns immediately — nothing else in the plugin boots at all without WooCommerce active.
  3. init_services() instantiates every service, in this order: Install, Blocks\Manager, Blocks\Interactivity, Blocks\Extensions, Blocks\Buy_Now, Patterns\Manager, Assets\Manager, Rest\Templates_Controller, Rest\Product_Reviews_Controller, Layouts\Post_Type, Layouts\Meta_Box, Layouts\Template_Override, Layouts\Duplicate, Layouts\Preview — then, only if ( is_admin() ): Admin\Dashboard.
  4. Every service is a singleton constructed via its own ::instance(), each registering its own hooks in its constructor rather than being wired externally — there's no central "add_action" list to maintain in Plugin itself.
  5. do_action( 'noorifa-core/loaded', $this ) fires once every service above exists — the hook a Pro or third-party add-on should use to register its own services, rather than hooking plugins_loaded directly and risking a load-order race.
  6. init handles textdomain, migrations, and registration that must wait for other plugins to have finished their own plugins_loaded: Plugin::load_textdomain(), Install::maybe_upgrade() (priority 5), Layouts\Post_Type::register(), Blocks\Manager::register_blocks(), Patterns\Manager::register_patterns().

The Layout system

A Layout is a post of type noorifa_core_layout, edited in the ordinary block editor. Nothing renders it directly — on every product-page request, Layouts\Resolver::get_layout_id() decides which Layout (if any) applies, checking each of these in order and stopping at the first match:

  1. Preview override — a nonce-verified ?noorifa_core_preview=ID query var from the Layout list's "Preview" row action. Works even for an unpublished Layout, gated by edit_post on that specific post.
  2. Product-level choice — post meta _noorifa_core_layout_id, set from the "Product Page Template" meta box on the product edit screen, if it points at a published Layout.
  3. Category-level default — term meta noorifa_core_layout_id on the product's product_cat terms, first match wins.
  4. Site-wide default — option noorifa_core_default_layout_id, set on the Noorifa Core Dashboard admin page.
  5. Nothing resolves — falls through to 0, and the product page renders exactly as WooCommerce/the active theme would without this plugin at all.

How the swap actually happens

Layouts\Template_Override hooks add_filter( 'template_include', ..., 100 ). Priority 100 is deliberate: WooCommerce's own class-wc-template-loader.php recomputes $template for product pages at its own priority, so this filter has to run after it to win. On is_product() requests where Resolver::get_layout_id() returns non-zero, $template is swapped for the plugin's own templates/single-product-layout.php.

That fallback template deliberately mirrors WooCommerce's real templates/single-product.php structure — same get_header('shop')/get_footer('shop'), same woocommerce_before_main_content / woocommerce_before_single_product / woocommerce_after_single_product / woocommerce_after_main_content / woocommerce_sidebar action firing, same $product global set via wc_get_product(). Where WooCommerce would normally render content-single-product.php, it instead does:

templates/single-product-layout.php
echo do_blocks( $layout->post_content );
ⓘ

Because every other WooCommerce structural hook still fires in its normal position, third-party plugins that hook woocommerce_before_single_product etc. (structured data, "recently viewed" trackers, upsell widgets) keep working identically around a Noorifa Core Layout — the override is a whole-template swap via template_include, never a the_content filter.

The "Product Page Template" meta box

Layouts\Meta_Box adds a side meta box to the Product edit screen: a dropdown of every published Layout (plus "— Default (theme/WooCommerce) —"), saved to _noorifa_core_layout_id on save_post_product. It also adds a "Default Product Page Template" field to the product category add/edit screens, saved as term meta and requiring manage_product_terms.

Templates & Patterns system

Bundled premade templates are plain JSON files under templates/library/, e.g. templates/library/bold-product-layout.json:

templates/library/bold-product-layout.json
{
    "title": "Bold Product Layout",
    "description": "…",
    "type": "layout",
    "category": "bold",
    "is_pro": true,
    "content": "<!-- wp:noorifa-core/product-title /-->…"
}

type is required (layout or section); description, category, and is_pro are optional (category falls back to type, is_pro falls back to false). content always ships in full — this is a single codebase, nothing is stripped for a "Free" build. A thumbnail is auto-detected from {dir}/thumbnails/{filename}.{png,jpg,webp}, no JSON field needed.

Patterns\Manager scans every configured directory (get_pattern_dirs(), filterable via noorifa-core/pattern_dirs — see below), caching the parsed result per-request and in a 1-day transient invalidated by an mtime fingerprint over every template + thumbnail file. Registration as native block patterns only happens where patterns are actually consulted (is_admin(), ajax, REST, or the noorifa-core/patterns_are_needed filter) — skipped on plain front-end requests.

⚠

Any directory other than the plugin's own templates/library/ has every template in it force-set to is_pro = true, regardless of that JSON's own is_pro field. That folder only exists on a site because some add-on contributed it, so nothing in it is ever free by definition — see Licensing & the Pro gate.

Where a directory can come from

The base directory list is just array( NOORIFA_CORE_DIR . 'templates/library' ), run through apply_filters( 'noorifa-core/pattern_dirs', $dirs ). Noorifa Core Pro is the one real example today — it appends its own templates/ folder (see Building a companion add-on).

Source aggregation (Templates\Repository)

The REST layer doesn't talk to Patterns\Manager directly — it goes through Templates\Repository, which merges every registered Source:

Local_Source

Wraps Patterns\Manager — the bundled (+ Pro add-on) JSON templates above. Implements Lazy_Source (fetches full content on demand).

Cloud_Source

Fetches a JSON array of templates from a remote URL (NOORIFA_CORE_CLOUD_URL or the noorifa-core/cloud_api_url filter), transient-cached 12h on success / 5min on failure. Inactive if no URL is configured.

Sources are filterable via noorifa-core/template_sources. On a name collision, the first source wins (bundled beats remote). The final merged, filterable-by-args collection is exposed via noorifa-core/library_templates.

Licensing & the Pro gate

Licensing\Gate is the single source of truth for every free/pro decision in the codebase — a plain static utility, not a singleton, because every check is a pure filter lookup with nothing to instantiate:

includes/Licensing/Gate.php
class Gate {

    public static function is_pro() {
        return (bool) apply_filters( 'noorifa_core_is_pro', false );
    }

    public static function has_feature( $feature ) {
        return (bool) apply_filters( "noorifa_core_feature_{$feature}", self::is_pro() );
    }

    public static function feature_keys() {
        return array();
    }
}

is_pro() defaults false — the real, permanent Free behavior. has_feature($key) defaults to the global flag but lets a future tiered license override one feature independently, without changing any call site. feature_keys() is currently empty — see the callout below for why, before adding anything to it.

⚠

This class must never be used to lock code that ships in this WP.org-hosted free plugin. The first submission was rejected under WP.org's Guideline 5 (Trialware) for exactly that: Split Testing and the Hero block's video background were fully implemented here but gated behind Gate::has_feature(), defaulting to disabled — WP.org's own words: "Even if the locked feature is present in the code 'just in case the user upgrades,' it's still not allowed," even as a dimmed/disabled upsell control. Both features were removed from this codebase (Hero's video background was simply unlocked for everyone instead, since it was a client-only static-block control with nothing server-side to re-gate). has_feature()/feature_keys() only remain valid for gating code that lives entirely in the separate Noorifa Core Pro plugin — never for anything physically shipped here.

How Noorifa Core Pro unlocks things

Noorifa Core Pro (a separate, sibling plugin, Requires Plugins: noorifa-core) never touches this plugin's internals directly — it only hooks the two extension points built for this purpose:

noorifa-core-pro/includes/Plugin.php
class Plugin {

    public static function init() {
        add_filter( 'noorifa_core_is_pro', array( __CLASS__, 'is_pro' ) );
        add_filter( 'noorifa-core/pattern_dirs', array( __CLASS__, 'add_template_dir' ) );
    }

    public static function is_pro() {
        return function_exists( 'nt_pro_fs' ) && nt_pro_fs()->can_use_premium_code();
    }

    public static function add_template_dir( $dirs ) {
        $dirs[] = NOORIFA_CORE_PRO_DIR . 'templates';
        return $dirs;
    }
}

nt_pro_fs() is the vendored Freemius SDK's accessor (initialized in noorifa-core-pro/includes/freemius-bootstrap.php against the plugin's own Freemius product). can_use_premium_code() is Freemius's own check for "this site has a valid license or active trial." The moment that's true, Gate::is_pro() flips to true everywhere in the free plugin — currently that only affects Rest\Templates_Controller/Patterns\Manager, which refuse to serve Pro-tier template content contributed by noorifa-core-pro's own templates/ directory (added via the noorifa-core/pattern_dirs filter above) unless licensed. That content physically lives only in the Pro plugin, never in this one — see the callout below for why that distinction matters.

ⓘ

This mirrors the sibling plugin NoorQuiz's own Core\Licensing design: the free plugin only ever exposes filter points, and a Pro add-on's entire job is hooking them with a real license check — nothing in the free codebase needs to know Freemius (or any licensing vendor) exists.

⚠

The only WP.org-compliant way to gate a feature is to keep its implementation entirely out of this repo. The Pro-templates pattern above (content lives only in noorifa-core-pro/templates/, contributed via a filter) is correct. Gating a feature that's physically present in this free plugin behind Gate::has_feature() — even just dimming/disabling its UI — is not, regardless of how solid the server-side enforcement is. See the callout in Licensing & the Pro gate above for what happened the one time this codebase did that.

Extending Noorifa Core

Extension points at a glance

Every extension point follows the same shape: a filter that returns an array (or a boolean), into which your own plugin pushes one more entry. Nothing requires editing Noorifa Core's own files.

New blockfilter

Add a directory containing a block.json to noorifa-core/block_dirs. Blocks\Manager auto-discovers and registers it the same way it registers the 29 built-in blocks.

New bundled templatefilter

Add your own directory to noorifa-core/pattern_dirs, matching the JSON shape in Templates & Patterns system. Every template found there is automatically treated as Pro-tier.

New template sourcefilter + class

Implement Templates\Source (or Lazy_Source for on-demand content) and add it via noorifa-core/template_sources — same shape as the bundled Cloud_Source.

Gate an add-on's own featurefilter

Gate::has_feature('your_key')/noorifa_core_feature_your_key exist for an add-on to gate a feature it implements and ships in its own plugin — never for locking code that physically lives in this free plugin. See the warning in Licensing & the Pro gate.

Disable a blockfilter

Add its name to noorifa-core/disabled_blocks — the same filter the Dashboard's block-toggle settings write to.

Full companion add-onfilter + plugin

Hook noorifa-core/loaded from a separate plugin to register your own services once Noorifa Core has fully booted — see below.

Building a companion add-on

Noorifa Core Pro is a real, working example of this pattern — not a hypothetical. It's a separate plugin folder, noorifa-core-pro, that does nothing but vendor the Freemius SDK and hook two filters.

1. Plugin skeleton

A companion plugin, not a modification of Noorifa Core itself — Requires Plugins lets WordPress core handle the dependency check (deactivation/warning if the free plugin is missing) with no custom code.

noorifa-core-pro.php
<?php
/**
 * Plugin Name:       Noorifa Core Pro
 * Description:       Unlocks Pro templates and Pro features for Noorifa Core.
 * Requires Plugins:  noorifa-core
 */

defined( 'ABSPATH' ) || exit;

define( 'NOORIFA_CORE_PRO_DIR', plugin_dir_path( __FILE__ ) );

require_once NOORIFA_CORE_PRO_DIR . 'includes/freemius-bootstrap.php';

require_once NOORIFA_CORE_PRO_DIR . 'includes/Autoloader.php';
\NoorifaCorePro\Autoloader::register();

add_action( 'plugins_loaded', array( '\NoorifaCorePro\Plugin', 'init' ) );

2. Hook the two filters

Shown in full in Licensing & the Pro gate above — noorifa_core_is_pro to unlock every Gate::has_feature() check at once, and noorifa-core/pattern_dirs to contribute the add-on's own templates/ folder so real Pro template content physically lives in the Pro plugin, never in the free one.

3. A more targeted alternative: hook a single feature

Gate::feature_keys() is currently empty (see Licensing & the Pro gate for why), but the mechanism stays available for an add-on gating a feature it ships itself. If an add-on should unlock one such feature rather than everything, it hooks the feature-specific filter instead of the global one:

PHP
add_filter( 'noorifa_core_feature_your_key', function () {
    return my_addon_has_a_valid_license();
} );

This leaves Gate::is_pro() itself untouched (so templates and any other global gate stay unaffected) while unlocking just that one feature.

4. Registering your own service once Noorifa Core has booted

For anything beyond the two filters above — a new admin page, a new block, a background job — hook noorifa-core/loaded rather than plugins_loaded, so every core service is guaranteed to already exist:

PHP
add_action( 'noorifa-core/loaded', function ( \Noorifa\Core\Plugin $plugin ) {
    \My_Addon\Service::instance();
} );

Other extension recipes

A new block

PHP
add_filter( 'noorifa-core/block_dirs', function ( array $dirs ) {
    $dirs[] = __DIR__ . '/build/blocks/my-block';
    return $dirs;
} );

The directory needs a block.json, same as any of the 29 built-in blocks under src/blocks/ — Blocks\Manager doesn't care whether the directory belongs to this plugin or an add-on.

A new bundled template

PHP
add_filter( 'noorifa-core/pattern_dirs', function ( array $dirs ) {
    $dirs[] = __DIR__ . '/templates';
    return $dirs;
} );

Drop .json files matching the schema in Templates & Patterns system into that directory, plus optional thumbnails in a thumbnails/ subfolder. Remember: every template found in an add-on-contributed directory is automatically Pro-tier, regardless of its own is_pro field.

A new remote template source

PHP
use Noorifa\Core\Templates\Lazy_Source;

class MyRemoteSource implements Lazy_Source {
    public function get_id() {
        return 'my-remote-source';
    }

    public function get_templates() {
        // Return an array of template metadata (no content).
    }

    public function get_template( $name ) {
        // Return one template's full content, or null.
    }
}

add_filter( 'noorifa-core/template_sources', function ( array $sources ) {
    $sources[] = new MyRemoteSource();
    return $sources;
} );

Working in this codebase

Development environment

You need a working WordPress site with WooCommerce active — Noorifa Core refuses to boot without it (see Boot sequence), so there's no way to work on it against a bare WordPress install.

RequirementNotes
WordPress6.6+ (Requires at least in the plugin header).
PHP7.4+ (Requires PHP in the plugin header).
WooCommerceActive on the same site — a hard dependency, not optional.
Node.jsWhatever current @wordpress/scripts requires (check its own engines field) — there's no .nvmrc pinned in this repo, so match your Node version to the installed @wordpress/scripts version if you hit build errors.
ComposerOptional — only needed for the PHP linting tools (wp-coding-standards/wpcs, PHPCompatibility), not for running the plugin itself.
  1. Place the plugin at wp-content/plugins/noorifa-core in a WordPress install that already has WooCommerce active (a product with at least one review is useful for testing the Reviews/Review Carousel blocks).
  2. Install JS dependencies: npm install.
  3. (Optional) install PHP dev tooling: composer install — only needed to run composer lint/lint:fix (PHPCS against WordPress Coding Standards).
  4. Start the watcher: npm run start — rebuilds build/ on every save under src/. Activate the plugin in wp-admin as normal; there's no separate dev-server/proxy, you're editing the real plugin the real site loads.
ⓘ

If you're also working on Noorifa Core Pro alongside the free plugin, install it as a normal sibling plugin at wp-content/plugins/noorifa-core-pro and activate both — it has no build step of its own (plain PHP + the vendored Freemius SDK), so there's nothing to npm install there.

Creating a new block

This walks through adding a block to this codebase directly (as opposed to registering an external block from a separate add-on plugin, which is a different recipe using the noorifa-core/block_dirs filter instead of the steps below). Every block lives in its own folder under src/blocks/; Blocks\Manager::get_block_dirs() auto-discovers every folder under the built build/blocks/* matching one via glob() and calls register_block_type( $dir ) on each — so a new block only needs the right files in the right shape, no manual registration call anywhere in PHP.

The minimum file set

The simplest real block in this codebase, Advanced Button (src/blocks/button/), is a good template to copy:

src/blocks/button/ ├── block.json # name, attributes, supports — the single source of truth WP reads at registration ├── index.js # registerBlockType() — wires block.json + Edit + save together ├── edit.js # the editor-side React component ├── save.js # static markup serialized into post_content (omit entirely for a dynamic block) ├── style.scss # front-end + editor styles └── editor.scss # editor-only styles
src/blocks/button/index.js
import { registerBlockType } from '@wordpress/blocks';

import metadata from './block.json';
import Edit from './edit';
import save from './save';
import './style.scss';
import './editor.scss';

registerBlockType( metadata.name, {
    edit: Edit,
    save,
} );
  1. Create the folder under src/blocks/your-block/.
  2. Write block.json — set "name": "noorifa-core/your-block", "category": "noorifa-core" (the plugin's own inserter category), and declare every attribute you need.
  3. Write edit.js — the Inspector controls and in-canvas editing UI. If the block should get the plugin's own icon picker or unique-id helper, reuse the shared components in src/utils/ rather than rebuilding them (icon-picker.js, use-unique-id.js). Don't wrap a control in a Pro-upsell gate unless the feature it controls ships entirely in a separate add-on — see Licensing & the Pro gate.
  4. Choose static or dynamic rendering: a static block ships a save.js whose output is serialized straight into post_content (fine for pure layout/content blocks with nothing to compute at render time). A dynamic block (any block that needs live WooCommerce data — see every Product block in Codebase map) has no save.js and instead declares "render": "file:./render.php" in block.json, which webpack copies alongside the built JS (--webpack-copy-php in the build script — see Build tooling & shipping).
  5. Run npm run start (or build for a one-off) — the block appears in the inserter under the "Noorifa Core" category as soon as build/blocks/your-block/block.json exists and the plugin's init hook re-runs (reload wp-admin).
ⓘ

Every Noorifa Core block automatically gains the shared Visibility/Animation Inspector panel and front-end behavior from src/extensions/ — you don't opt in explicitly, it's applied to any block whose name starts with noorifa-core/. If your new block is dynamic, double-check its render.php actually applies the visibility classes/animation data-attributes itself; the extension's save-props filter only fires for static blocks' save.js output.

Working in this codebase

Conventions & gotchas

  • Every service is a singleton via the shared Singleton trait (protected constructor, cloning disabled) — access an already-booted service through its own ::instance(), never new.
  • Meta and option keys are always class constants, never inline string literals — e.g. Resolver::PRODUCT_META_KEY. Reference the constant, not the raw string, so a rename only touches one place.
  • An add-on's contributed template directory is always Pro-tier, regardless of the JSON's own is_pro field — see the callout in Templates & Patterns system. Don't rely on setting is_pro: false in an add-on's own template to make it free; it won't work, by design.
  • Never lock a feature that's physically implemented in this repo, even editor-UX-only. This is the hard rule the first WP.org submission was rejected over — see the warning in Licensing & the Pro gate before adding anything to Gate::feature_keys().
  • No the_content filtering anywhere. The single-product override is a whole-template swap via template_include at priority 100 — keep it that way if you're touching Layouts\Template_Override, since filtering content instead would break the WooCommerce structural hooks other plugins depend on.
  • Blocks\WP_Icon_Registry is generated, not hand-written — it mirrors the @wordpress/icons package via scripts/generate-icon-registry.js. Regenerate it rather than editing it directly if the icon set changes.

Noorifa Core Pro has no build step of its own today — it's plain PHP plus the vendored Freemius SDK, so shipping it is just zipping the folder directly.

Shipping a release

  1. Bump the version in two places: the Version: header in noorifa-core.php (which also sets the NOORIFA_CORE_VERSION constant), and Stable tag: in readme.txt. Unlike NoorQuiz's release script, nothing in this codebase cross-checks these automatically today — they can silently drift, so bump both by hand every time.
  2. Run npm run release — builds build/ fresh, then zips exactly the paths listed in package.json's files array (currently noorifa-core.php, readme.txt, includes, patterns, templates, build) via wp-scripts plugin-zip. src/ and node_modules/ are never included — only compiled output ships.
  3. Sanity-check readme.txt separately from the version bump — it's a real wp.org-format readme (Requires at least, Tested up to, Requires PHP, feature list), not a stub, so keep its description in sync with what actually shipped.
⚠

As of this writing, noorifa-core.php's header version and readme.txt's Stable tag/package.json's version are already out of sync (1.1.0 vs 1.0.0) — a concrete example of exactly the drift the step above warns about. Worth reconciling before the next release.
